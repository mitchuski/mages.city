## 1 · The correction — the City is not live

**`mages.city` does not serve the City. It serves the registrar's parking page.**

The 2026-09-05 record says *"mages.city FRONT LIVE (Cloudflare Workers, board D1; probed 200)"*.
The probe was a status code, and the status code was 200 — but on the wrong page. What the apex
actually returns, today, is 114 bytes:

```html
<!DOCTYPE html><html><head><script>window.onload=function(){window.location.href="/lander"}</script></head></html>
```

That is the GoDaddy parking lander, byte for byte the same body `agentprivacy.org` returns. Both
zones now answer from Cloudflare nameservers, so the move happened; the parking record came across
with the zone and nothing has replaced it.

| checked | result |
|---|---|
| `mages.city` NS | `anna` / `kanye.ns.cloudflare.com` — moved ✓ |
| `mages.world` NS | Cloudflare ✓ |
| `agentprivacy.org` NS | Cloudflare ✓ — **moved since the 09-05 note, which still says GoDaddy** |
| `mages.earth` NS | `ns07/08.domaincontrol.com` — still GoDaddy |

| `npx wrangler whoami` | **Not logged in** — `wrangler deploy` has never run from this machine |

So **D1 is open, not done.** Nothing was lost and nothing is broken: the deploy simply never
happened. The lesson is cheap and worth keeping — *a 200 is not a deployment.* Probe for a byte
of your own page, never for a status code.

The fix, in order, is the keeper's (three commands and one dashboard visit):

   and `www` — `wrangler` will refuse to claim a custom domain while they sit there.

4. Verify with content, not a code: `curl -s https://mages.city/ | grep -c "the board opens next"`.
5. The same for `agentprivacy.org` from `~/agentprivacy_labs`.

Until then `docs/LAUNCH_2026-09-05.md` must not be published: its line *"Today the front of

## 3 · What was integrated — the City now reads the signature beside the key

The two lanes shared a design and nothing else. `agentprivacy-mcp` signs a **VTA record** beside
the City Key and offers it to this repo through a `cityKey` slot on a resident's `proofs` page
(`agentprivacy-mcp/docs/WEAVE_mages-city.md`). This repo **never consumed it**: `site/data.js` read
`proofs.packets.length` and nothing else, so the standing chip *counted* — the one thing the whole
design says it must not do. Meanwhile `gate/citykey.mjs` could re-derive κ but could not check a
signature at all.

**First, the seam was measured before it was crossed.** Both lanes derive κ independently; if their
canonical forms disagreed by one byte, wiring them together would make the City refuse real records
in public. They agree — proven on six real keys exported from the live site (`~/Downloads/city-key-*.json`),
κ identical on both sides, every stamped κ re-deriving.

**Then the join.** New and changed here:

- **`site/record.js`** (new) — the City's verifier. WebCrypto only, so *one file* serves both the
  browser chip and `bin/verify.mjs` in node. It ports `verifyRecord` · `verifyCard` · `evolvedSince`
  from the other lane's `lib/sign.mjs`, adds `readCityKeySlot()` (what the chip is allowed to say),
  and derives κ and `did:key` with the same canonical rule `gate/citykey.mjs` uses.
- **`site/data.js`** — `resident()` now recomputes the AgentCard's ceremony signature and reads the
  `cityKey` slot through the verifier. `chip()` reports `κ <8 hex> verified`, or `stale` past the
  90-day horizon, or `unproven`. A resident with no record is *less shown, never lower scored*.
- **`bin/build-pages.js`** — the twin now signs a **real** ed25519 record for `soulbis` (demo keypair
  in `.run/`, gitignored, never in the kit — checked) so the acceptance suite exercises the whole
  path instead of a hand-written fixture. `soulbae` publishes none: verified and unproven stand side
  by side on the front, which is the honest picture.
- **`bin/verify.mjs`** — nine new rows, including the **anti-drift rows**: if either lane ever changes
  its canonical form, its `did:key` derivation, or the bytes it signs over, the City would start
  refusing genuine records. That now fails here, loudly, instead of in public.

The chip that used to read `⚔️ blade · unproven · 25/25 carried` now reads:

```
⚔️ blade · κ e710114a verified · 3 walks · 25/25 carried · vouched ×0
```

and an edited walk count, a re-labelled κ, a record paired with the wrong key, a card belonging to
another agent, and a signature past its horizon are each refused **by name**. This closes the two
`NEXT` rows in `DECISIONS_2026-09-05.md` §2 — *"the City Key reader → the chip's core"* and *"the
standing chip → recomputed on load"* — and it is the whole of the keeper's rule *nothing is a score*,
made mechanical: the chip holds no number it did not just recompute from a signature.

## 4 · The VTA farm — where it actually stands

Unchanged since 09-05, and correctly so. The operator CLIs (`pnm` `cnm` `vta-mcp` `didcomm-test`)
built clean; the two **services** (`vta.exe`, `vtc.exe`) did not, needing a Visual Studio Spectre-libs
component. That blocker never needed solving: **D4 rules the farm onto Linux**, where it does not
exist. Windows was the build box, never the host.

So the farm is not behind a bug — it is behind a host decision. `deploy/viewer/decisions.json` records
the keeper's choices (profile **B** sovereign · edge **pi4** · VTI on the edge · bare systemd · vault
secrets · keeper as first CTA) with only step **A** marked done, and A is the step §1 just showed is
half-finished. The order in `AGENTIC_VTI.md` §6 still holds: the board goes up before any VTA. A VTA
farm with no board is a server.

One thing worth naming: the local Swordsman built in the other lane is *already* a working VTA in
everything but the name — it holds the identity, signs the records, and the City now verifies them.
`vta.mages.city` (OpenVTC `vta-service`) does not replace it; it hosts it for agents that cannot hold
their own seed. The bridge between the two is the same `did:key`, and it is now tested.
