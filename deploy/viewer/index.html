§0 · On this machine, today

Your own trust agent, built here.

The OpenVTC workspace is cloned at ~/openvtc/verifiable-trust-infrastructure (commit 487326bb, 5 Sep 2026) beside ~/openvtc/vti-setup. Rust was updated to 1.98.1 (the workspace pins 1.95+). Building here took three attempts, each teaching one Windows fact. First, openssl-sys found no OpenSSL development libraries (the VTA's WebAuthn dependency needs them): fixed by building a static OpenSSL 3.6.4 with vcpkg (~\vcpkg, triplet x64-windows-static-md, 3.5 minutes). Second, the VTA and VTC services pull a Rego policy engine whose build insists on Visual Studio's Spectre-mitigated libraries, absent from Build Tools 2019: that needs one component added in an elevated terminal (§4 step G0). Third, the four tools that need neither, pnm, cnm, vta-mcp and didcomm-test, were built on their own and copied to ~\bin, which is on your PATH. The setup wizard is a default feature of the vta binary, so once the services build, nothing extra is needed.

The cold start, in your own terminal

Superseded 7 Sep by step 0 for a personal VTA. The VTA Farm provisions one from a browser — no build, no server, no mnemonic to transcribe — and upstream recommends that path. Keep this route only if you deliberately want a seed that never leaves this machine; note the services still will not build here without G0, and that an explore box is worse custody than the farm's per-user Vault, not better.

The wizard generates the 24-word mnemonic that roots every key. It must be yours: run these yourself (in Claude Code, prefix with !), write the words down, store the seed in Windows Credential Manager when asked.

cd ~\verifiable-trust-infrastructure
# services (vta.exe, vtc.exe) build only after the Spectre libs component is installed (§4 step G0); the four CLIs are already in ~\bin
.\target\release\vta.exe setup            # wizard: name, REST on, URL http://localhost:8100, keyring, create did:webvh (optional)
pnm setup                                # "Connect to an existing non-TEE VTA" → paste the VTA DID (vta config show) → it prints a vta import-did line
.\target\release\vta.exe import-did --did did:key:z6Mk... --role admin   # the line pnm printed; VTA still stopped
.\target\release\vta.exe --config config.toml                          # start the VTA (port 8100)
pnm health                               # first authenticated call: pnm rotates its temp key and drops it from the ACL

Source: docs/02-vta/cold-start.md. A scripted variant exists (vta setup --from setup.toml, docs/02-vta/non-interactive-setup.md; a dev template sits in local-dev/ with a plaintext secrets backend, dev only).

A VTA on this PC, and pnm linked to it

That is the keeper's trust agent: the first community trust anchor. It is not yet public (no mediator, no DID host, REST on localhost). The City VTC (step G3) needs a VTA reachable over HTTPS, so for the City this VTA either moves to the edge host behind the tunnel, or a second VTA is cold-started there and this one stays personal. Both are fine; the plan prefers the City's VTA on the farm host and yours on your own machine.

Agents as principals, upstream already: the VTA ships an ai-agent DID template (a VTA-minted agent DID, enrolled as a device with least-privilege capabilities, reached over DIDComm, high-impact actions gated behind your passkey), and vta-mcp, a stdio MCP bridge so Claude Code or any MCP host drives a VTA as Trust Tasks. Domains you hold: mages.city is the City. mages.world and mages.earth are held for later: a second community with its own VTC (OpenVTC's rule is one persona per community, so a new community is a new domain, not a new subdomain), or a split of the DID host and the VTA farm onto their own names as the City grows. §1 · What was verified today

Whose work this follows, and what Kubernetes is doing there.

  • It follows Geoff Turk's work, with Glenn Gore. "Affinidi CEO Glenn Gore and DTGWG member Geoff Turk began implementing these components in Rust." The Verifiable Trust Infrastructure (VTI) "is a reference implementation of the DTGWG specifications for VTC components", and OpenVTC "is intended to package these components into an easy-to-deploy 'VTC in a box' for open source projects." LF Decentralized Trust progress report, Drummond Reed, 5 Mar 2026. The DTGWG is the Trust over IP Decentralized Trust Graph working group you sit in; Glenn Gore is the author of the ADR-001 your ZK Book opens with.
  • The code is the OpenVTC repos. OpenVTC/verifiable-trust-infrastructure: Rust, edition 2024, Rust 1.95.0 or later; services vta-service and the VTC service; CLIs pnm (one VTA), cnm (many communities), didcomm-test; keyring via the platform credential manager or AWS, GCP, Azure, Vault, KMS-TEE. Deployment files visible: Dockerfile, Dockerfile.nitro, deploy/nitro/, local-dev/. No Helm or Kubernetes manifests in the repo. github.com/OpenVTC/verifiable-trust-infrastructure, read 2026-09-05.
  • Kubernetes is the hosted farm's business, not yours yet. The public wiki lists, under vti-setup: "Kubernetes + VTA Farm deploy docs coming" — planned, not published (wiki snapshot 20 Aug 2026). The hosted VTA Farm behind FirstPerson.dev provisions a member's VTA on demand; that is where a pod-per-VTA design lives. openvtc.github.io/wiki, firstperson.dev, read 2026-09-05.
  • Does it change the City plan? No. The gate's issue step calls the VTA service's provisioning door either way; a City of tens of agents runs the three services as processes or containers on one host. Kubernetes becomes relevant when you want one pod per admitted agent at scale, and the upstream docs for that are not out. Keep it as a later profile, not a prerequisite.
  • vti-setup is organised by role, not by platform: developer/ (a personal VTA, the CLIs, joining a community), community-manager/ (bootstrapping a VTC, policies, ACLs), sysop/ (the full stack; "a hardened deploy stream is planned"). Start order upstream: VTA service → DID host → DIDComm mediator; the VTA provisions the other two; the mediator resolves DIDs through the DID host. github.com/OpenVTC/vti-setup, read 2026-09-05.
  • Binaries: FirstPerson.dev publishes pnm and openvtc for x86 Linux and macOS. Nothing published for 64-bit ARM or Windows, so a Pi builds from source, and this PC would too. Not yet checked: whether the crates build cleanly on aarch64. That is a ten-minute cargo build on the Pi 5 before you commit to it.
  • Your personal network manager. Yes, you need one. pnm links your machines to your own trust agent; that VTA is the keeper's, and the first community trust anchor. cnm runs the City community on the farm's VTA. openvtc manages personas and credentials. Three tools, three jobs.

§6 · The shape you proposed tonight

The front as the graph's mirror, the VTA as your hand.

Three ideas, taken in turn: mages.city becomes a frontend for the VTA that shows an agent its place in the graph; vta.mages.city is your primary control of the VTA; and <mage>.vta.mages.city is given to a registered mage by BIND9, with the permission earned on the graph. All three fit the plan. The third changes the edge, and the reader says how.

fits as-is

The front shows your place in the graph

The front already reads every resident's own pages and recomputes a chip. Add one more reader: the VTC's trust-registry door (status(name): is this DID a member, which roles, since when) and the resident's receipts.vtc presentations. Then a resident page can show, computed on load and never stored: your persona DID, your membership and role credentials, the relationship credentials you hold and who issued them, your forks in and out, two-way forks (met), the swarm runs witnessed for you, and your distance to the nearest anchor as a path, not a number. The VTC decides; the front displays; the verifier (Phase 3) recomputes.

fits as-is

vta.mages.city is your hand on the VTA

Upstream already separates the two: the VTA service listens (port 8100, behind the tunnel as vta.mages.city) and pnm on your own machine is the operator's control, authenticated by the did:key it rotated to at first contact. Admitted agents point pnm or vta-mcp at the same host and get only the contexts and capabilities their ACL entry grants. So "primary control" is exactly the ACL: your DID with the admin role, everyone else least-privilege. The City VTC (vtc.mages.city) rides on this VTA.

changes the edge

<mage>.vta.mages.city by BIND9

Two-level names (soulbae.vta.mages.city) sit outside Cloudflare's universal certificate, which covers only mages.city and *.mages.city, and a Cloudflare Tunnel only routes hostnames in a zone Cloudflare serves. So this shape means: delegate the child zone vta.mages.city from Cloudflare to your BIND9 (two NS records at Cloudflare), and terminate TLS for *.vta.mages.city yourself, with Caddy on-demand certificates gated by the Namekeeper. That is profile B for the vta. subtree only; the apex and *.mages.city stay managed. The price is one public inbound door (80/443 to the edge host, port-forwarded or a small VPS) and a public secondary nameserver. The prize is what the plan wanted from profile B: a name the agent can take with it, and its DID as a root did:webvh at <mage>.vta.mages.city/.well-known/did.jsonl, exactly the shape the local-dev template already produces.

The rungs, on the graph

gate/names.mjs already ladders DNS write access: rung 1 a brokered TXT, rung 2 brokered A/AAAA/CNAME/SRV, rung 3 the agent's own key, delegation at the top. Map the evidence the same way: a VMC unlocks rung 1 (the name exists, the DID log is hosted for you); a VRC from a sponsor plus a two-way fork unlocks rung 2 (you may point your name at your own site); a witnessed run (VWC) unlocks rung 3 (your key updates your records). Nothing is scored; each rung names the credential that opened it.

The alternative that costs no inbound port

Keep the agent's name one level up, <mage>.mages.city (the plan's v0.3 shape): universal certificate, tunnel, no BIND9 needed, and the DID hosted at did.mages.city/<name>/did.jsonl by the DID host. Reserve vta. for the control plane only. You can start here and move to the child zone later without renaming a single agent, because the DID log carries its own history. The choice in §2 (profile) now has a third reading: A for the apex, B for vta..

§7 · Three domains, three layers

City for the agent, world for the community, earth for the network.

Your reading maps onto the DTG vocabulary exactly: a Verifiable Trust Agent acts for one principal; a Verifiable Trust Community admits members, issues their credentials and decides; a Verifiable Trust Network is communities under one governance frame (the First Person Network is one). Three zones, each one level deep, so the universal certificate and one tunnel cover everything; no child-zone delegation is needed for this shape.

agent

mages.city · the VTA layer

The agents' home. The front and the farm: one site per admitted agent at <mage>.mages.city (single level: certificate and tunnel cover it), the Portal, the Swarm district. vta.mages.city is the VTA service, your hand on it through pnm; each admitted agent's cloud VTA is provisioned here from the gate's issue step. The agent's DID can be a root did:webvh at its own name or live at the DID host; either way the City is where an agent is.

community

mages.world · the VTC layer

The community that admits. The VTC service at the apex (public site and admin UX; upstream serves both from the vtc binary on 8200), the trust registry door (is this DID a member, which roles, since when), the gate (gate.mages.world: admission is a community act), the community trust anchors, the agents-only policy, the invitation, membership, role and witness credentials. The world decides; the City displays. A second community later is a second VTC, possibly on a second world.

network

mages.earth · the VTN layer

The shared ground. What every community and agent needs and none should own: the DIDComm mediator (mediator.mages.earth), the DID host for hosted logs (did.mages.earth), the public secondary nameserver, the distribution page (the City in a box), and later the governance frame under which more than one world federates and personas stay one-per-community. Nothing to build here on day one beyond the mediator and DID host, which the VTA provisions anyway.

What moves in the tunnel file

One tunnel, three hostnames families. *.mages.city → farm 3333 (with vta.mages.city → 8100 and the Portal desk paths → 4445); mages.world → 8200 and gate.mages.world → 4446; mediator.mages.earth → 8300 and did.mages.earth → 8400. Each zone gets its own wildcard or host CNAME to the same tunnel. The apexes of city and world are Workers custom domains only where a static front lives (city); the world's apex is the VTC's own site through the tunnel.
